# Эталонный тест качества протоколов (Д16)

Меряет качество протокола не «на глаз», а метрикой — гоняется **перед каждым
релизом** и при любой правке промпта / смене модели.

## Как добавить эталонную встречу

Каталог `cases/<имя-встречи>/` с файлами:

| Файл | Что это |
|---|---|
| `transcript.txt` | таймкодированная расшифровка встречи (как выдаёт система: `[мм:сс] реплика`, с именами спикеров, если были) |
| `notes.txt` | *(опционально)* живые заметки участника — подаются как `user_notes` |
| `reference.json` | эталонный протокол — заметки коллег + ручная выверка |
| `meta.json` | *(опционально)* `{"demo": true}` — демо-кейс, не реальная встреча |

Формат `reference.json`:

```json
{
  "tasks":      [{"task": "что сделать", "owner": "Имя или null"}],
  "done_tasks": [{"task": "что сделано", "owner": "Имя или null"}],
  "decisions":  ["что решили", "..."],
  "topics":     ["тема 1 (короткое название сути)", "..."],
  "facts": [
    {"fact": "Выкатить теги на прод до среды", "kind": "task", "owner": "Кирилл"},
    {"fact": "Оставить пять базовых фильтров", "kind": "decision"},
    {"fact": "тип периода привязан к ролям", "kind": "status", "status": "не сделано"}
  ]
}
```

⚠️ **Главное в эталоне — `facts`: чек-лист обязательных фактов, а не
«идеальный протокол»** (docs/ТЗ-МЕТРИКИ.md И23). Согласие двух разметчиков на
уровне целого пересказа низкое — один напишет три темы, другой семь, и оба
правы. На уровне отдельных фактов («решение X принято», «задача Y на человеке
Z», «на вопрос W ответ — не сделано») оно приемлемое. Факт ищется по ВСЕМУ
протоколу — задачам, решениям, статусам, темам: важно, что он есть, а не в
какой колонке. `owner`/`status` сверяются только там, где заданы.

Правила выверки эталона:
- `facts` — 10–25 фактов, без которых протокол этой встречи бесполезен;
  формулировать коротко и по существу, без стилистики модели;
- в `tasks` — ВСЕ задачи, которые реально прозвучали (включая мелкие);
- `owner` только если на встрече это было сказано явно; иначе `null`;
- `topics` — все содержательные темы в хронологическом порядке.

## Регламент (И23—И25)

- **Размер набора — 25–40 встреч**, по типам (планёрка, дизайн-ревью, демо,
  1:1, стратсессия) и длительностям (20 мин / час / 2+ часа). Одна встреча
  каждого сорта — это ещё не набор.
- **Треть обновлять раз в квартал.** Промпт и модель подстраиваются под
  старые кейсы сами собой; свежие встречи возвращают метрике смысл.
- **Пять кейсов — закрытые:** `meta.json: {"closed": true}`. На них не
  смотреть при правках промпта, они не гоняются по умолчанию — только
  финальной проверкой `--closed`. Иначе промпт подгоняется под эталон, и
  число растёт, а качество нет.
- **Прогон перед каждой сменой модели или промпта** — регламент, а не
  метрика дашборда. Скрипт сам печатает дельту к прошлому прогону на том же
  движке (из `history.jsonl`); отрицательная дельта по `facts_coverage` или
  рост `unsupported_share` — стоп-сигнал.
- **Чужие встречи — только с письменным разрешением клиента** (И67), обезличенно
  и в отдельном хранилище; проще всего — свои.

## Запуск

```bash
# в контейнере (нужен доступ к LLM — Ollama на хосте или ключи):
docker cp tests linux-voise:/tmp/eval
docker compose exec -T app sh -c "chown -R app /tmp/eval && cd /tmp/eval/.. \
  && PYTHONPATH=/app gosu app python /tmp/eval/eval/run_eval.py --provider ollama"

# либо прямо из репозитория при локальном питоне с зависимостями:
python tests/eval/run_eval.py --provider ollama
```

Ключи: `--provider` (движок протокола), `--cases имя1,имя2` (подмножество),
`--no-verify` (без grounding-прохода), `--strict` (ненулевой код выхода при
провале порогов — для CI), `--closed` (включить закрытые кейсы — только
финальная проверка).

## Метрики и пороги релиза

- **task recall ≥ 0.90** — доля эталонных задач, найденных протоколом;
- **owner accuracy ≥ 0.95** — среди найденных задач ответственный совпадает
  (пустой/«—» считается «не назначен» и обязан совпадать с эталонным null);
- **facts coverage ≥ 0.85** — доля обязательных фактов, найденных в протоколе
  (считается, только если в эталоне есть `facts`);
- unsupported share — доля пунктов без опоры в расшифровке по итогам
  проверки цитат (нужен прогон с проверкой); facts status accuracy, task
  precision, decisions recall, topics coverage — справочно.

Каждый прогон дописывает строку в `history.jsonl` (время, git-коммит, движок,
метрики по кейсам и сводные) — история изменения качества видна по файлу.
