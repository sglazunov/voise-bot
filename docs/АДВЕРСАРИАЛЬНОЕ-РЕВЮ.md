# Адверсариальное ревю linux-voise

Задача была одна: доказать, что проект ломается. Не «стоит улучшить», а
«вот вход → вот поломка», каждая — падающим тестом.

## Резюме

| | |
|---|---|
| Задумано атак (гипотез) | **20** |
| **Подтверждено тестом** | **11** (29 падающих тестов) |
| Не подтвердилось | **9** (8 проходящих тестов + 1 недостижимый путь) |

Тесты: `tests/adversarial/`. Прогон:

```bash
cd /d/linux-voise && "C:\Users\user\AppData\Local\Programs\Python\Python312\python.exe" -m pytest -q
# было:  327 passed
# стало: 29 failed, 335 passed   (все 29 — новые атаки; ни один прежний тест не тронут)
```

Ничего в `app/`, `frontend/`, `docker/`, `scripts/` не изменено — только
добавлены тесты и этот файл.

Общая картина: **самая дорогая вещь в проекте — единственный экземпляр записи
встречи, и именно он защищён хуже всего.** Четыре из одиннадцати находок
(A1, A2, A3, A4) — разные способы потерять его; три из них уже чинили в
прошлом (K5, `_late_upload`), но тот же дефект живёт рядом, в другой функции.

## Подтверждённые находки

### A1. Ретеншн удаляет исходник и результаты у задачи, которая ещё в работе

**Где:** `app/jobs.py:736` (`_purge_old`), отбор по возрасту в `app/jobs.py:742`
**Класс:** потеря данных

**Сценарий атаки:**
1. `VTX_RETENTION_HOURS` по умолчанию 24 (`app/config.py:58`), воркер
   распознавания ровно один, очередь общая.
2. Днём записаны четыре встречи по 2–4 часа. Коэффициент распознавания ~0.7
   (CLAUDE.md) — очередь легко уезжает за сутки; после любого простоя сервиса
   тем более.
3. `_cleaner_loop` раз в 30 минут зовёт `_purge_old()`. Тот берёт
   `ref = job.finished_at or job.created_at` и **не смотрит на статус**:
   `queued`, `running`, `analyzing` — всё равно.
4. Задача удаляется из памяти, а `_delete_job_files` стирает `audio_path`
   (это и есть mp4-запись встречи), `.txt/.srt/.json/.docx`.
5. Если выгрузка в облако не прошла (её ретраит `_late_upload`, и он первым
   делом проверяет `if not Path(out).exists(): return`) — записи больше нет
   нигде.

**Тест:**
`tests/adversarial/test_retention_eats_active_jobs.py::TestRetentionVsActiveJobs::test_queued_job_keeps_its_source`
`…::test_running_job_keeps_its_source`
`…::test_analyzing_job_keeps_its_transcript`
`…::test_purged_job_is_not_resurrected_in_the_database`

**Вывод теста:**
```
AssertionError: задача из очереди удалена ретеншном
AssertionError: идущая задача удалена ретеншном
AssertionError: ретеншн стёр расшифровку задачи на этапе анализа
AssertionError: удалённая ретеншном задача воскресла в базе без единого файла —
                после перезапуска она вернётся в список как «Готово»
```

Четвёртый тест — второй виток той же гонки, уже на Postgres. `_save(job)` теперь
пишет ОДНУ задачу (`db.job_upsert`), а воркер держит свою ссылку на `Job` и
после очистки продолжает работать: его следующий `_set(...)` **заново вставляет
строку** задачи, которой в памяти нет и у которой стёрты все файлы. После
перезапуска `jobs_load()` поднимет её в список.

**Почему это важно:** встреча исчезает молча, без строки в журнале и без
карточки — доказать, что она вообще была, нечем. На Postgres вместо этого
появляется карточка-призрак «Готово», у которой скачивание любого формата
отдаёт 404.

### A2. Сбой посреди встречи снова теряет готовую запись (затенённый логгер)

**Где:** `app/automation/recorder/__init__.py:113` (`log = on_log or (lambda *_: None)`)
перекрывает модульный логгер `log` из строки 23; вызовы `log.warning` —
строки **258** и **274**
**Класс:** потеря данных

**Сценарий атаки:**
1. Бот час пишет встречу, файл на диске растёт.
2. Посреди встречи что-то падает (перевёрстка Телемоста, сеть, база) — обычное
   дело, ради него и появился пункт K5 ревью «сбой посреди встречи не должен

   даёт сбой (ffmpeg уже умер сам). Это `except Exception:` → `log.warning(...)`.
4. `log` здесь — **функция** `on_log`, а не логгер. `AttributeError` вылетает
   ИЗ обработчика ошибок и уносит управление мимо спасательного блока
   (строки 264–272), который вернул бы `{"ok": True, "path": …}`.
5. `Scheduler._run` ловит исключение и ставит карточке `error`. Состояние
   `error` не входит в `pending`, `_resume_pending` такую встречу не подбирает.

**Тест:**
`tests/adversarial/test_recorder_rescue_lost.py::test_finished_recording_survives_a_mid_meeting_failure`
`…::test_record_meeting_never_raises_attributeerror`

**Вывод теста:**
```
app\automation\recorder\__init__.py:258: AttributeError: 'function' object has no attribute 'warning'
Failed: record_meeting уронил обработчик собственных ошибок: 'function' object has no attribute 'warning'
```

**Почему это важно:** ровно та потеря, которую закрывали пунктом K5. Файл лежит
на диске целый, но его никто не выгрузит, не распознает и не подберёт после
перезапуска — час встречи пропадает из-за секундной ошибки.

### A5. Круговой рейс настроек уничтожает токен Weeek, а интерфейс продолжает
### показывать «подключено»

**Где:** `app/automation/settings.py:49` (`isinstance(val, str)` в
`_transform_secrets`) + `app/api_automation.py:62` (`automation_save` не
проверяет типы)
**Класс:** потеря данных / порча конфигурации

**Сценарий атаки:**
1. `GET /api/automation/settings` отдаёт секреты как **признак наличия**:
   `{"weeek_token": true, "yandex_disk": {"token": true, …}}` (`redacted`).
2. Клиент делает обычное «прочитал — поправил одно поле — сохранил» и шлёт
   объект обратно в `POST /api/automation/settings`.
3. `AutomationSettings.known()` пропускает `weeek_token`, потому что ключ
   есть в `_DEFAULTS`. `_transform_secrets` шифрует **только строки**, поэтому
   `True` ложится в хранилище как есть.
4. Настоящий токен затёрт безвозвратно. `redacted()` снова отдаёт `true` —
   карточка Weeek показывает «подключено».
5. Планировщик проходит проверку `if not cfg.get("weeek_token")` (`True` —
   истина) и каждые две минуты ходит в Weeek с заголовком `Bearer True`.
   Встречи просто перестают появляться.

**Тест:**
`tests/adversarial/test_settings_secret_wipe.py::TestSecretRoundTrip::test_module_level_roundtrip_keeps_the_token`
`…::test_api_roundtrip_keeps_the_token`
`…::test_nested_cloud_secret_survives_roundtrip`
`…::test_ui_does_not_claim_connected_after_the_wipe`

**Вывод теста:**
```
AssertionError: круговой рейс подменил токен на True
AssertionError: POST тем, что отдал GET, стёр токен Weeek
AssertionError: круговой рейс стёр OAuth-токен Яндекс Диска
AssertionError: токена нет, а карточка Weeek по-прежнему показывает «подключено»
```

**Оговорка честности:** нынешний фронтенд так не делает — он аккуратно шлёт
токен только когда его ввели заново (`Weeek.tsx:29`, `Cloud.tsx:30-33`,
`Scheduler.tsx:77`). То есть сегодня это не воспроизводится кликами в UI, но
воспроизводится любым другим клиентом API и любой правкой фронта, где эту
осторожность забудут. Сервер обязан отбивать такой ввод, а не молча съедать.

**Почему это важно:** автоматика умирает без единого сообщения об ошибке,
а единственный индикатор («подключено») врёт. Восстановление — выпустить новый
токен Weeek и OAuth заново.

### A6. `re` не импортирован в `llm_base` — вся защита от лимитов движка мертва

**Где:** `app/llm_base.py:47` (`re.search` в `_retry_after`), при импортах в
строках 8–13 без `re`
**Класс:** зависание/срыв конвейера, порча результата

**Сценарий атаки:**
1. Движок отвечает **429 или 503 без заголовка `Retry-After`**. У Groq это
   штатное поведение: подсказка лежит в ТЕЛЕ («Please try again in 12.34s») —
   именно ради неё регулярка в `_retry_after` и написана.
2. `_http_post_json` заходит в `if e.code in (429, 503) …: _retry_after(...)`
   → `NameError: name 're' is not defined`.
3. Ретрай не происходит вообще. NameError уходит наверх.
4. `_is_rate_limit(NameError("name 're' is not defined"))` → `False`. Значит
   `_RotatingProvider` **не паркует ключ и не переключается на следующий**
   (вся многоключевая ротация, пункт V8 ревью, не работает), а
   `_FallbackChain` считает движок «сломанным» и уходит на следующий.

Это регрессия разреза `llm.py 1211 → 656` (`llm_base` ← `llm_nvidia` ← `llm`):
`_retry_after` переехала, `import re` — нет.

**Тест:**
`tests/adversarial/test_llm_rate_limit.py::TestRetryAfter::test_body_hint_is_parsed`
`…::TestRetryAfter::test_no_hint_falls_back_to_default`
`…::TestHttpPostJsonRetries::test_429_without_header_is_retried_not_crashed`
`…::TestHttpPostJsonRetries::test_rate_limit_error_is_recognised_as_such`

**Вывод теста:**
```
D:\linux-voise\app\llm_base.py:47: NameError: name 're' is not defined. Did you forget to import 're'
AssertionError: ошибка NameError: name 're' is not defined — не опознана как упор
                в лимит, ключи ротироваться не будут
```

(Ветка с заголовком `Retry-After` работает — соответствующий тест проходит.
Именно поэтому дефект не виден: он включается только там, где заголовка нет.)

**Почему это важно:** «добавьте ещё один ключ» — стандартный совет самого
приложения при 429 (`jobs._friendly_error`). Второй ключ не поможет: до
ротации дело не доходит. Протокол либо соберёт запасной движок (в шапке —
«Выбранный движок не ответил»), либо не соберёт никто.

### A7. «Пересобрать» поверх работающего воркера: два прогона ИИ на одну задачу

**Тест:**
`tests/adversarial/test_double_protocol_run.py::test_reanalyze_refuses_a_job_the_worker_is_analysing`
`…::test_reanalyze_refuses_a_job_still_being_transcribed`

**Вывод теста:**
```
tests\adversarial\test_double_protocol_run.py:68: Failed: DID NOT RAISE ValueError
tests\adversarial\test_double_protocol_run.py:76: Failed: DID NOT RAISE ValueError
```

**Почему это важно:** в задаче Weeek оказываются две разные ссылки на протокол
одной встречи, а в приложении — протокол, который выиграл гонку. Плюс два

### A8. У повторяющейся встречи заметки и живая расшифровка уходят в чужую карточку

### A11. Восстановление пароля — оракул перебора «логин + телефон»

**Где:** `app/main.py:361` (`return {**_RECOVER_SENT, "retry_after": …}`),

**Класс:** утечка

**Сценарий атаки:**
1. Шаг 1 восстановления намеренно отвечает одинаково в любом случае — это

   `generate_recovery_code` («must otherwise stay silent — no account

сдвинул границу молча.
