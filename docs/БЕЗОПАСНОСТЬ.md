# Безопасность и авторизация

Приложение рассчитано на публичный домен, поэтому весь доступ закрыт за входом, а
данные и токены каждого пользователя изолированы и зашифрованы.

## Модель

- **Гейт авторизации.** HTTP-middleware (`app/main.py::_auth_gate`) пропускает без
  сессии только `/login`, `/register`, `/healthz` и сами auth-API. Всё остальное:
  HTML — редирект на `/login`, API — `401`.
- **Сессии.** При входе выдаётся непредсказуемый токен (`secrets.token_urlsafe(32)`)
  в cookie `vtx_session` (**HttpOnly**, `SameSite=Lax`, `Secure` при `VTX_HTTPS=1`).
  Срок — `VTX_SESSION_TTL_HOURS` (по умолч. 7 дней). Хранятся в `data/sessions.json`.
- **Пароли.** Никогда не хранятся в открытом виде — только PBKDF2-HMAC-SHA256
  (200 000 итераций, индивидуальная соль). Сравнение — постоянное по времени.
- **Шифрование секретов.** Токены Weeek/облаков шифруются на диске (Fernet/AES).
  Ключ — серверный master-key (`VTX_SECRET_KEY`, иначе генерируется в
  `data/secret.key`), из него через HKDF выводится **отдельный ключ под каждый
  логин**. Чужой логин расшифровать секреты не может.
- **Изоляция данных.** Настройки/токены — в `data/users/<логин>/automation.json`;
  записи — в `data/users/<логин>/recordings/`; задачи распознавания помечены
  владельцем, и каждый per-job эндпоинт проверяет `job.owner == текущий_логин`.
  Планировщик гоняет автоматизацию для каждого пользователя под его токенами.

### Компромисс (осознанный)
Шифрование — это «шифрование на диске + контроль доступа», **не** zero-knowledge:
сервер может расшифровать секреты, потому что бот должен работать 24/7, пока
пользователь оффлайн. Для zero-knowledge пришлось бы отказаться от фоновой
автозаписи. Master-key держите вне репозитория (env `VTX_SECRET_KEY`), а каталог
`data/` — приватным (права `0600` на файлах секретов).

## Регистрация (политика)
- Первый аккаунт создаётся свободно и становится администратором.
- Дальше регистрация требует код `VTX_REGISTRATION_CODE` (или открыта при
  `VTX_ALLOW_OPEN_REGISTRATION=1`). Без кода и без флага — закрыта.

## Переменные окружения
| Переменная | Назначение |
|---|---|
| `VTX_SECRET_KEY` | master-key шифрования секретов (задайте свой!) |
| `VTX_REGISTRATION_CODE` | код приглашения для регистрации после первого юзера |
| `VTX_ALLOW_OPEN_REGISTRATION` | `1` = открытая регистрация |
| `VTX_SESSION_TTL_HOURS` | срок жизни сессии (по умолч. 168) |
| `VTX_HTTPS` | `1` = ставить cookie с флагом `Secure` (за HTTPS-прокси) |

## Тест-кейсы
`tests/test_auth_security.py` (запуск: `pytest -q`). 23 кейса:

**Гейт:** аноним → `/api/*` = 401; HTML → редирект `/login`; `/login`,`/register`,
`/healthz` открыты; настройки анониму = 401.

**Регистрация:** первый юзер ок + сессия (cookie HttpOnly); короткий пароль = 400;
неверный логин = 400; дубликат = 400; после первого юзера без кода = 400; неверный
код = 400, верный = 200.

**Логин:** верные данные ок; неверный пароль = 401; неизвестный юзер = 401; выход
аннулирует сессию; поддельный токен = 401.

**Секреты:** сохранённый токен отдаётся как флаг присутствия (не plaintext); на
диске зашифрован; пароль на диске — только PBKDF2-хеш.

**Изоляция:** юзер не видит токен другого (ни через API, ни при расшифровке); задача
одного не видна/не скачивается другим (404).

**Крипто:** хеши пароля уникальны (соль) и проверяются; шифр секрета различается по
пользователю, чужим ключом не расшифровывается; пустой секрет остаётся пустым.
