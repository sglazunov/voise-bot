# Безопасность и авторизация

Приложение рассчитано на публичный домен, поэтому весь доступ закрыт за входом, а
данные и токены каждого пользователя изолированы и зашифрованы.

## Модель

- **Гейт авторизации.** HTTP-middleware (`app/main.py::_auth_gate`) пропускает без
  сессии только `/login`, `/register`, `/healthz` и сами auth-API. Всё остальное:
  HTML — редирект на `/login`, API — `401`.
- **Сессии.** При входе выдаётся непредсказуемый токен (`secrets.token_urlsafe(32)`)
  в cookie `vtx_session` (**HttpOnly**, `SameSite=Lax`, `Secure` при `VTX_HTTPS=1`).
  Срок — `VTX_SESSION_TTL_HOURS` (по умолч. 7 дней). Хранятся в таблице `sessions`
  (без базы — в файле; см. БЕКЕНД §14).
- **Пароли.** Никогда не хранятся в открытом виде — только PBKDF2-HMAC-SHA256
  (200 000 итераций, индивидуальная соль). Сравнение — постоянное по времени.
- **Шифрование секретов.** Токены Weeek/облаков шифруются на диске (Fernet/AES).
  Ключ — серверный master-key (`VTX_SECRET_KEY`, иначе генерируется в
  `data/secret.key`), из него через HKDF выводится **отдельный ключ под каждый
  логин**. Чужой логин расшифровать секреты не может.
- **Изоляция — по КОМАНДЕ** (см. «Регистрация и команды»). Единица изоляции —
  команда, а не отдельный логин: настройки/токены, записи, задачи и контекст
  хранятся и шифруются под логином **админа команды** (`security.team_of`).
  Участники одной команды видят общие данные (это и есть смысл приглашения);
  между разными командами доступа нет — каждый per-job эндпоинт проверяет
  `job.owner == team_of(текущий_логин)`. Планировщик гоняет автоматизацию **один
  раз на команду** под токенами её админа. При хранении в Postgres — те же данные
  в таблицах, ключ изоляции тот же (`team` / `username` админа).

### Компромисс (осознанный)
Шифрование — это «шифрование на диске + контроль доступа», **не** zero-knowledge:
сервер может расшифровать секреты, потому что бот должен работать 24/7, пока
пользователь оффлайн. Для zero-knowledge пришлось бы отказаться от фоновой
автозаписи. Master-key держите вне репозитория (env `VTX_SECRET_KEY`), а каталог
`data/` — приватным (права `0600` на файлах секретов).

## Регистрация и команды (мульти-тенант)
Модель — команды. Каждый аккаунт принадлежит **команде**, определяемой логином
её админа (`user.team`). Всё общее (настройки, токены Weeek/облака, LLM-ключи,
AI-контекст, встречи, задачи распознавания) хранится и **шифруется под логином
админа команды**, поэтому участники прозрачно работают на конфигурации админа.

Регистрация на `/register` (всегда открыта, поле кода — опциональное):
- **Без кода** → новый аккаунт становится **админом своего окружения**: `team =
  свой логин`, `is_admin = true`, генерируется персональный **код приглашения**.
- **С валидным кодом** → аккаунт вступает в команду того админа, чей это код:
  `is_admin = false`, `team = <админ>`. Неверный код → ошибка.

Админ видит свой **код приглашения во вкладке «Профиль»** (`invite_code_of`).
Передал код → человек регистрируется с ним и получает доступ к
настройкам/секретам/ключам админа.

**Код приглашения:**
- **ротируется раз в сутки** (`INVITE_CODE_TTL`, env `VTX_INVITE_CODE_TTL_SEC`):
  просроченный код никого не пускает, свежий выдаётся при заходе в профиль; срок
  действия показан рядом с кодом;
- **не одноразовый** — пока код жив, по нему может войти сколько угодно людей;
- 8 hex-символов, хранится в `users.invite_code` (+ `invite_code_at`); подбор
  ограничен тем же rate-limit регистрации (8 попыток/15 мин на IP), сравнение —
  `hmac.compare_digest`.

**Управление командой (в профиле админа):** список логинов рабочего пространства
(`team_member_list`) и кнопка **«Исключить»** (`POST /api/profile/team/remove` →
`security.remove_from_team`). Исключённый сохраняет логин, но получает СВОЁ пустое
окружение (`team` = свой логин) и **все его сессии сразу отзываются** — доступ к
данным команды пропадает мгновенно. Исключить себя нельзя; исключать может только
админ своей команды.

Автоматика (`scheduler`) крутится **один раз на команду** (по токенам админа), а
не на каждого участника — без дублей записей. Ключевые функции:
`security.team_of / invite_code_of / team_members / list_teams`.

**Удаление аккаунта:** участник удаляет только свой логин (данные команды не
трогаются, они под админом). Админ, у которого есть участники, удалиться не
может — сперва нужно удалить участников (иначе общий воркспейс осиротеет).

**Админ команды ≠ админ сервера.** `is_admin` = владелец своей команды (таких
почти все). Глобальные операции сервера (установки пакетов, серверный HF-токен)
доступны ТОЛЬКО **основателю** — самому первому зарегистрированному аккаунту
(`security.is_super_admin`, `require_admin`). Иначе любой, кто зарегался без кода,
смог бы менять инфраструктуру общего хоста.

Пароль — минимум 6 символов (`MIN_PASSWORD_LEN`). Отдача статики SPA закрыта от
path-traversal (файлы только внутри `frontend/dist`), чтобы залогиненный
пользователь не мог прочитать `secret.key` или учётки через `../`.

> На будущее: под подписку одна команда = один тенант/подписка. Ограничение на
> создание новых команд (регистрация без кода) можно будет добавить отдельным
> флагом, когда появится биллинг.

## Защита от перебора (brute force)
Логин и регистрация ограничены скользящим окном: **8 неудачных попыток за 15
минут** на IP (и на пару IP+логин) → дальнейшие попытки получают `429` до
остывания окна. Удачный вход сбрасывает счётчик. Настройка:
`VTX_LOGIN_MAX_ATTEMPTS` / `VTX_LOGIN_WINDOW_SEC`. За реверс-прокси задайте
`VTX_TRUST_PROXY=1`, чтобы IP брался из `X-Forwarded-For`.

## Сессии на диске
Хранится **SHA-256 от токена**, а не сам токен: утёкшая копия
файла не позволяет угнать сессию — сырой токен существует только в cookie
пользователя.

## Роли
Две РАЗНЫЕ роли — не путать:

- **Админ команды** (`is_admin`) — владелец своего рабочего пространства. Таких
  почти все: любой, кто зарегистрировался без кода приглашения. Управляет только
  СВОЕЙ командой: её настройки и ключи, код приглашения, состав участников.
- **Админ сервера / основатель** (`is_super_admin`) — самый первый
  зарегистрированный аккаунт, ровно один. Только ему доступны операции над общим
  хостом: установка пакетов (`apt`/`pip`), установка Ollama, серверный HF-токен
  (`require_admin` → `403` всем остальным).

Разделение обязательно: без него любой, кто завёл себе команду, мог бы менять
инфраструктуру сервера, общую для всех команд.

## Восстановление пароля по телефону (SMS-код)
При регистрации обязателен **номер телефона** (нормализуется до цифр, «8…» = «+7…»)
и **уникален** — один номер привязан максимум к одному аккаунту (проверяется при
регистрации и при смене телефона в профиле — `security._phone_owner` под общим
локом, чтобы два одновременных запроса не заняли один номер).
Забыли пароль → `/recover` — **двухшаговый** сброс через одноразовый код:

1. **Запрос кода** (`POST /api/auth/recover/request`): логин + телефон совпали →
   генерируется 6-значный код, хранится **только его PBKDF2-хеш** (соль, срок
   жизни `VTX_RECOVERY_CODE_TTL_SEC`=10 мин, счётчик попыток), а сам код уходит
   пользователю по **SMS** (`app/sms.py`). Ответ сервера **всегда одинаков**
   («если данные верны, код отправлен») — не раскрывает, существует ли логин.
2. **Ввод кода** (`POST /api/auth/recover/verify`): код + новый пароль. Верный
   код → новый пароль + **отзыв всех сессий**. Код **одноразовый** и сгорает
   после `VTX_RECOVERY_MAX_ATTEMPTS`=5 неверных попыток; повторная отправка — не
   чаще `VTX_RECOVERY_RESEND_SEC`=60 с (анти-спам SMS).

**SMS-шлюз** выбирается автоматически: **SMS.ru** при заданном `VTX_SMSRU_API_ID`,
иначе «console»-заглушка (код только пишется в лог — для разработки/до настройки
шлюза). Параметры — в `.env.example` (`VTX_SMSRU_*`, `VTX_SMS_PROVIDER`).

Обе ручки под тем же **rate-limit** (8/15 мин на IP и IP+логин). Смена телефона
в профиле требует **текущий пароль** — угнанная сессия не может переписать телефон
на свой. Смена пароля в профиле — по старому паролю **или** по телефону.

## Заголовки безопасности
Каждый ответ получает `X-Frame-Options: DENY` (кликджекинг),
`X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`; при
`VTX_HTTPS=1` — ещё и `Strict-Transport-Security` (HSTS).

## Переменные окружения
| Переменная | Назначение |
|---|---|
| `VTX_SECRET_KEY` | master-key шифрования секретов (задайте свой!) |
| `VTX_INVITE_CODE_TTL_SEC` | срок жизни кода приглашения (по умолч. 86400 — сутки) |
| `VTX_SESSION_TTL_HOURS` | срок жизни сессии (по умолч. 168) |
| `VTX_HTTPS` | `1` = cookie `Secure` + HSTS (за HTTPS-прокси) |
| `VTX_TRUST_PROXY` | `1` = брать IP из `X-Forwarded-For` (только за прокси) |
| `VTX_LOGIN_MAX_ATTEMPTS` / `VTX_LOGIN_WINDOW_SEC` | порог/окно анти-брутфорса |

## Чек-лист публичного запуска
1. **HTTPS обязательно**: реверс-прокси (Caddy/nginx + Let's Encrypt) перед
   портом 8000; в compose привяжите порт к `127.0.0.1:8000`.
2. Задайте `VTX_HTTPS=1` и `VTX_TRUST_PROXY=1` (cookie Secure, HSTS, верный IP).
3. Задайте свой `VTX_SECRET_KEY` (вне git). **Не меняйте его после запуска** —
   иначе уже сохранённые токены/ключи не расшифруются.
4. Зарегистрируйте первого пользователя **сразу после** запуска: он становится
   основателем (единственный, кому доступны серверные операции).
5. **Осознайте открытую регистрацию.** Сейчас аккаунт на публичном адресе создаст
   кто угодно (он получит своё пустое окружение, чужие данные ему не видны). Если
   это неприемлемо — закройте доступ на уровне прокси/VPN: в приложении
   переключателя «запретить новые команды» пока нет (появится вместе с подпиской).
6. `data/` + named volume `pgdata` — приватные (бэкапьте вместе с `secret.key`).
7. Обновляйте образ (`git pull && docker compose up -d --build`).

## Тест-кейсы
`tests/test_auth_security.py` (запуск: `pytest -q`). 40 кейсов:

**Гейт:** аноним → `/api/*` = 401; HTML → редирект `/login`; `/login`,`/register`,
`/healthz` открыты; настройки анониму = 401.

**Регистрация:** первый юзер ок + сессия (cookie HttpOnly); короткий пароль = 400;
неверный логин = 400; дубликат = 400; после первого юзера без кода = 400; неверный
код = 400, верный = 200.

**Логин:** верные данные ок; неверный пароль = 401; неизвестный юзер = 401; выход
аннулирует сессию; поддельный токен = 401.

**Секреты:** сохранённый токен отдаётся как флаг присутствия (не plaintext); на
диске зашифрован; пароль на диске — только PBKDF2-хеш.

**Изоляция:** юзер не видит токен другого (ни через API, ни при расшифровке); задача
одного не видна/не скачивается другим (404).

**Крипто:** хеши пароля уникальны (соль) и проверяются; шифр секрета различается по
пользователю, чужим ключом не расшифровывается; пустой секрет остаётся пустым.
