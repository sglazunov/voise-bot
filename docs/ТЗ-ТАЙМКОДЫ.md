# ТЗ: таймкод основания берётся из расшифровки, а не от модели

Составлено 03.09.2026 по разбору кода и замеру на шести боевых протоколах.
Ссылки на файлы и строки — на состояние `main` от 03.09.2026.

## 1. Зачем

Под каждым подтверждённым пунктом протокола стоит строка вида
«Основание [04:46]: «надо обновить сервер»». Цитата в ней настоящая — её
дословность проверяется механически. Время рядом с цитатой — нет: его называет
модель, и оно расходится с расшифровкой вплоть до целого часа. Человек
открывает запись на названной минуте и слышит другой разговор.

**Цель.** Время в основании — это время той реплики расшифровки, в которой
найдена цитата. Модель времени больше не сообщает; её ответ используется только
как подсказка при выборе между несколькими одинаковыми репликами.

**В объём НЕ входит** (отдельные работы, здесь не описываются): снятие меток
времени из текста, уходящего в модель, и проверка цитат по окну расшифровки.

## 2. Замер, на котором построено решение

86 пар «заявленный таймкод и цитата» из шести боевых протоколов:

| Показатель | Значение |
|---|---|
| Цитата найдена в расшифровке | 100 % (83 дословно — 97 %, 3 приблизительно) |
| Дословные цитаты, встречающиеся ровно один раз | 83 из 83 |
| Время модели точно (0 секунд) | 35 % |
| Отклонение до 5 секунд | 44 % |
| Отклонение до 30 секунд | 73 % |
| Отклонение больше минуты | 16 % |
| Отклонение больше пяти минут | 7 % |
| **Заявленных таймкодов, которых нет среди меток расшифровки** | **20 из 82 — 24 %** |

Примеры (цитаты дословны и единственны): «со следующей недели мы его точно сюда
призовём» — в одном прогоне 96:34, в другом 06:34, истина 36:34. «Ну вообще
здесь предполагалось пока вот она на главной» — заявлено 66:54 и 06:54, истина
1:06:54: ошибка ровно на час в обе стороны. «Ну, путь мы, по-моему, уже выбрали,
что мы берем новый проект» — заявлено 07:37, реально 47:46. «Давай скан сделаю,
пришлю» — одна фраза получила в одном протоколе два времени, 50:55 и 51:00, при
единственном вхождении на 51:01.

Границы применимости проверены намеренной порчей цитат: обрезка до 6 слов —
находится 99 %, до 3 слов — 97 % (из них 4 % неоднозначны), порча 15 % слов —
87 %, порча 30 % — 5 %. **Промахов с неверным временем нет ни на одном уровне
шума**: метод деградирует в отказ, а не в ложный ответ. Точность ограничена
шагом между метками: медиана 5 секунд, 86 % шагов не больше 10 секунд.

## 3. Как работает сейчас

Время приходит в запись двумя путями, и у обоих есть цитата:

- от модели — `_norm_t(item.get("t"), labels, max_min)` (analyze.py:1471-1474);
- из механического поиска опоры — `_find_support` возвращает `t` по метке
  найденной строки (analyze.py:1482-1486, сам поиск — :1237-1287).

### Находка 1. Защита от ложного часа на бою не срабатывает ни разу

`verify_protocol` собирает метки расшифровки шаблоном `\[(\d{1,3}):(\d{2})\]`
(analyze.py:1424), а боевая расшифровка пишется `formats.to_txt` в формате
`[чч:мм:сс]` (formats.py:18-22, 31-38). Шаблон требует закрывающую скобку сразу
после двух цифр, поэтому `[00:04:46]` под него не подходит. Проверено: на
боевом формате набор `labels` **пуст**, `max_min` — `None`, ни одна поправляющая ветка `_norm_t`
не срабатывает (analyze.py:1014-1038 — обе опираются на `labels` и `max_min`),
и «96:34» остаётся «96:34». Тесты этого не поймали: фикстуры написаны в формате `[мм:сс]`.

Сопутствующее: промпты обещают модели метки вида `[мм:сс]`
(analyze_prompts.py:251, 253, 255, 260, 264, 273, 278), а видит она `[чч:мм:сс]`
— отсюда и дописанные часы.

### Находка 2. У большинства строк расшифровки метки нет вовсе

`to_txt` при известном говорящем ставит метку только в шапке блока
(`[00:04:46] Зоя Р:`), сами реплики идут голыми строками (formats.py:31-38). На
образце боевого формата из пяти непустых строк метку несут две. Значит
восстановление обязано **наследовать** метку от последней шапки, иначе больше
половины цитат останутся без времени. Отсюда честная формулировка результата:
мы даём «время реплики говорящего», а не «время строки». Имена говорящих есть у
56–72 % реплик боевых расшифровок (замер по шести файлам, обычно около 70 %,
участников 5–8 на встречу).

### Мелочь, которая тоже неверна

Цитата из заметок участника (`source: "notes"`, analyze.py:1473) получает
модельный таймкод, хотя в заметках времени нет вовсе.

## 4. Требования

### 4.1. Источник времени

| № | Требование |
|---|---|
| Т1 | Время в основании берётся из расшифровки по найденной цитате. Проверка: каждое время протокола встречается среди меток расшифровки этой же встречи. Сейчас не встречается каждое четвёртое. |
| Т2 | Время, названное моделью, в запись не попадает никогда. Оно используется только как подсказка выбора между реальными вхождениями цитаты. |
| Т3 | Локатор возвращает **все** вхождения цитаты. Их число кладётся в запись проверки, чтобы масштаб неоднозначности был виден в данных, а не угадывался. |
| Т4 | Одно вхождение — берётся оно. Несколько и есть подсказка модели — берётся вхождение, ближайшее к подсказке. Несколько без подсказки — первое. |
| Т5 | Цитата короче `_MIN_QUOTE_CHARS = 10` (analyze.py:959) не ищется и времени не получает: «Да, беру» повторяется на встрече десятками. |
| Т6 | Строка без собственной метки наследует секунду последней метки выше по тексту (шапка блока говорящего). |
| Т7 | Цитата, пересекающая границу двух строк, получает время первой из них. |
| Т8 | Формат вывода — как в просмотрщике расшифровки: `мм:сс` до часа, `ч:мм:сс` начиная с часа. Форма «73:01» не выдаётся: она не совпадает ни с расшифровкой, ни с просмотрщиком. |
| Т9 | Цитата не найдена — время не ставится, а подтверждение (`ok`, `match`, ответственный) не меняется **ни при каких обстоятельствах**. Восстановление времени не умеет опровергать пункты. |
| Т10 | Цитата из заметок участника (`source: "notes"`) остаётся без времени: в заметках времени нет. |
| Т11 | Подмена времени — одна функция, вызываемая в `verify_protocol` один раз, после `_refine_tasks` (analyze.py:1487) и до сборки `ver["stats"]`. |
| Т12 | Локатор не строже нынешней сверки `_Fragment.match` (analyze.py:1082-1099): якорь берётся по самому редкому слову цитаты, а не по первому. Иначе опечатка в первом слове уводит поиск. |
| Т13 | `_norm_t` (analyze.py:1001-1037) и `_T_RE` (analyze.py:997) удаляются целиком: после правки вызовов не остаётся. |
| Т14 | Поле времени в заметках карты (`analyze_schemas.py:37-60`) не трогается: оно работает ключом дедупликации в зоне перекрытия кусков и задаёт порядок в промпте сведения. |
| Т15 | Ни один пункт не теряет время, которое у него было, кроме цитат из заметок — там оно было фиктивным. |

### 4.2. Пункты без цитаты

| № | Требование |
|---|---|
| Т16 | Пункт, у которого цитаты нет, не остаётся без времени: ему ставится приблизительное время, найденное по словам самого пункта, с явной пометкой. **Порог поиска для времени ОБЯЗАН быть ниже порога подтверждения**, иначе требование не даёт ничего — см. врезку ниже. Предлагается 0,35 против нынешних 0,6; окончательное значение подобрать на боевых протоколах и записать сюда. |
| Т16.1 | Поиск времени НЕ подтверждает пункт: `ok`, `match` и ответственный не меняются. Пункт остаётся в разделе «Требуют проверки», просто теперь у него есть ориентир, где это место в разговоре. |
| Т16.2 | Если и на пониженном пороге место не нашлось, пункт остаётся без времени. Это ожидаемый исход, а не дефект. Долю таких пунктов замерить на боевых протоколах и записать в этот раздел после первой раскатки. |

> **Врезка: почему без понижения порога требование Т16 бессмысленно.**
> Механический поиск опоры уже сегодня прогоняется по ВСЕМ неподтверждённым
> пунктам (analyze.py:1478-1486) и при удаче делает пункт подтверждённым:
> `ok = True`, `match = "approx"`, строка речи становится цитатой. Значит
> пункты, дошедшие до конца без цитаты, — это ровно те, на которых поиск уже
> отработал и вернул пустоту (порог `best < 0.6`, analyze.py:1275). Повторный
> вызов той же функции с тем же порогом найдёт ровно столько же, то есть
> ничего. Замер «спасает один пункт из десяти» относится к УЖЕ работающему
> проходу, а не к добавке. Новое здесь только одно: более мягкий порог,
> который даёт ориентир по времени, не выдавая его за подтверждение.
| Т17 | Значок «≈» из Word и интерфейса убирается совсем и заменяется словами (§4.3). Причина: он и так читался плохо, а теперь на него претендуют два разных смысла — «цитата приблизительная» и «времени нет, место угадано». Значок различить их не может, слова могут. Ни при каких условиях «≈» не должен означать отсутствие основания. |
| Т18 | Три случая различимы словами и в Word, и в интерфейсе (формулировки — §4.3). Читатель обязан отличить «цитату слегка перефразировали» от «основания нет вовсе». |

### 4.3. Формулировки подписей

| Случай | Word (docx_export.py:57) | Интерфейс (Protocol.tsx:28) |
|---|---|---|
| Цитата дословная | `Основание [04:46]: «…»` | `основание · 04:46` |
| Цитата приблизительная (`match=approx`) | `Основание [04:46], цитата приблизительная: «…»` | `основание · 04:46 · цитата приблизительная` |
| Цитаты нет, время по словам пункта | `Основания нет; в разговоре об этом — примерно [04:46]` | `без основания · примерно 04:46` |
| Цитата из заметок участника | `Основание (из заметок участника): «…»` | `основание · из заметок` |

Голый значок «≈» из обоих мест убирается: он плохо читается, а смыслов, которые
на него претендуют, стало два. Строка «Требуют проверки» в Word и во фронте
остаётся как есть — она про подтверждение, а не про время.

### 4.4. Совместимость и стоимость

| № | Требование |
|---|---|
| Т19 | Индекс времени строится один раз за вызов `verify_protocol` и по той же речи, что уже вычислена на analyze.py:1420 (после вырезания служебных блоков). Отдельного разбора расшифровки не заводится. |
| Т20 | Стоимость: построение индекса на 900 строк — не больше 20 мс (замер 9 мс), один поиск — доли миллисекунды. На фоне запросов к модели это ноль. |
| Т21 | Старые протоколы не пересчитываются: миграции нет, пересчёта на лету нет. Обоснование: ретеншн сносит задачу и расшифровку через сутки (`VTX_RETENTION_HOURS=24`, config.py:59, jobs.py:833-868), то есть «старые протоколы» — это протоколы последних суток, и через сутки их не будет независимо от нас. |
| Т22 | *По желанию.* Раздел «Что спрашивали и что ответили» может получить время тем же механизмом. Сейчас это невозможно без правки схемы: цитата теряется по дороге, в финальной `ProtoStatus` (analyze_schemas.py:108-112) полей цитаты и времени нет. Отдельный пункт, в основной объём не входит. |

## 5. Технические ограничения

- **Нормализация совпадает побайтово.** Проверено на пяти корпусах: построчная
  нормализация `_norm_for_match` (analyze.py:1065-1069), склеенная пробелами,
  равна нормализации всего текста целиком. Значит индекс ищет по той же строке,
  по которой проверка признаёт дословность, и случай «цитата подтверждена, но
  локатором не найдена» по причине нормализации невозможен.
- **Порядок вызова важен.** `_refine_tasks` (analyze.py:1330-1359) перекладывает
  записи между списками: задача, оказавшаяся уже сделанной, уезжает в «Сделано»
  (analyze.py:1352-1355), а опровергнутая теряет `ok`. Подмена времени до этого
  шага работала бы по устаревшим индексам списков.
- **Точность ограничена шагом меток**, а не алгоритмом: медиана 5 секунд, 86 %
  шагов до 10 секунд. Обещать секунду в секунду нельзя.
- **Два формата меток**: `[мм:сс]` в тестовых фикстурах и `[чч:мм:сс]` на бою.
  Индекс обязан понимать оба; регулярное выражение `_LINE_T_RE`
  (analyze.py:998) уже понимает, `_LABEL_RE` (analyze.py:996) тоже.
- **Строк без метки больше половины** (находка 2) — наследование обязательно,
  иначе цитаты из тела блока времени не получат.

## 6. Порядок работ

1. **Индекс времени.** По речи с analyze.py:1420 построить список строк: для
   каждой — смещение в нормализованном тексте и секунда последней встреченной
   метки (наследование). Единица работы, отдельно тестируемая.
2. **Локатор цитаты.** По нормализованной цитате вернуть все вхождения (смещение
   и время). Якорь — самое редкое слово цитаты (Т12), порог длины — Т5,
   мягкое совпадение не строже `_Fragment.match`.
3. **Одна функция подмены.** Обходит `_VERIFIED_LISTS`, у каждой записи с
   цитатой ставит время по правилам Т4, кладёт число вхождений, у записей без
   цитаты выполняет Т16. Вызов — на analyze.py:1487, после `_refine_tasks`.
4. **Удаление `_norm_t` и `_T_RE`** (Т13) и снятие `labels`/`max_min`
   (analyze.py:1424-1425), которые после этого не нужны.
5. **Подписи в Word и во фронте** по таблице §4.3.
6. **Тесты** по §8, включая удаление устаревших.

## 7. Пограничные случаи

| Случай | Ожидаемое поведение |
|---|---|
| Цитата через границу двух строк | Время начальной строки |
| Строка-продолжение внутри блока говорящего | Наследует метку шапки блока |
| Цитата не найдена | Время не ставится; подтверждение не трогается |
| Цитаты нет, место найдено на пониженном пороге | Приблизительное время с подписью «основания нет»; пункт остаётся неподтверждённым |
| Цитата из заметок участника | Остаётся без времени |
| Пункт опровергнут следующими репликами (`ok` снят в `_refine_tasks`) | Время не ставится: основания больше нет |
| Пункт переехал в «Сделано» | Время ставится по его цитате, как у любого подтверждённого |
| Цитата короче 10 символов | Не ищется, времени нет |
| Цитата встречается дважды, подсказки модели нет | Первое вхождение, число вхождений — в записи |
| Цитата встречается дважды, подсказка есть | Вхождение, ближайшее к подсказке |
| Расшифровка вовсе без меток | Времени нет ни у одного пункта; протокол собирается как обычно |

   стоит время метки.

## 9. Как проверить на бою

Приёмочный критерий, проверяемый без инструментов: после раскатки пересобрать
одну встречу и взять каждое время из строк «Основание». Каждое из них должно
находиться поиском по расшифровке этой же встречи. Сейчас так не находится
каждое четвёртое (24 % по замеру §2).

Второй прогон — на встрече длиннее часа: убедиться, что времена после часа
записаны как `1:06:54`, а не `66:54`, и что запись открывается на нужной минуте.

Диагностика, если время не встало:

```bash
docker compose logs app | grep 'vtx.analyze' | tail -20
```

Ожидание по видимости: доля подтверждённых пунктов и `match` не меняются —
восстановление времени на проверку цитат не влияет (Т9). Если доля
подтверждённых просела, правка задела проверку и её надо откатывать.
