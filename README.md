# linux-voise

Сервис **распознавания речи** и **сборки протоколов встреч** (Телемост) для Linux.
Разворачивается одной командой через **Docker Compose** — одинаково локально и на
сервере. Приватный: доступ только по логину/паролю, данные и токены каждого
пользователя изолированы и зашифрованы.

**Что умеет:**
- распознавание речи из аудио/видео (faster-whisper, локально) → TXT / SRT / JSON;
- протокол встречи в **Word (.docx)** через LLM (Ollama локально или Groq / GigaChat /
  YandexGPT / Gemini / Claude по ключу — с выбором тарифа модели);
- OCR текста с экрана (слайды/код на видео);
- интеграция с **Weeek** и выгрузка записей в **облако** (Я.Диск / Google Drive / локально);
- **бот-рекордер Телемоста** — Chromium заходит на встречу в виртуальном дисплее
  (Xvfb) и пишет экран + звук (ffmpeg x11grab + PulseAudio), без звука от самого бота.

Аудио/видео никуда не уходят, кроме случаев, когда вы сами выбираете облако для
записей или облачный LLM для протокола.

## Требования

- **Linux** (Ubuntu 22.04+ или любой дистрибутив с Docker). Проект рассчитан
  только на Linux — разворачивается на сервере/виртуальной машине.
- **Docker** + **Docker Compose v2** (`docker compose version`).
- ОЗУ: ~2 ГБ для модели `small`; **+1–2 ГБ** для бота (Chromium+Xvfb). Комфортно от
  **4 ГБ**. Ollama на сервер не ставится (подключается снаружи) — под неё память
  на этом сервере не нужна.
- Первая сборка образа — несколько минут (ставится ffmpeg, tesseract, Chromium).

Установка Docker на чистом Ubuntu:
```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"     # затем перелогиньтесь (или newgrp docker)
```

## Запуск локально

```bash
git clone https://github.com/sglazunov/linux-voise.git
cd linux-voise
cp .env.example .env
# пароль базы обязателен — без него compose не стартует
sed -i "s/^POSTGRES_PASSWORD=.*/POSTGRES_PASSWORD=$(openssl rand -hex 16)/" .env
docker compose up -d --build
```

Откройте **http://localhost:8000** → страница входа. Зарегистрируйте первый аккаунт
(он станет администратором, код не нужен — см. «Аккаунты»).

- Логи: `docker compose logs -f app`
- Остановить: `docker compose down`
- Проверка: `curl http://localhost:8000/healthz`

## Раскатка на сервере

1. Поставьте Docker (см. выше) и склонируйте репозиторий на сервер.
2. Создайте `.env` и задайте **свой** ключ шифрования секретов и пароль базы
   (без пароля `docker compose` не стартует; на **новой** установке
   `DATABASE_URL` compose собирает сам из `POSTGRES_*` — в `.env` его не
   задавайте. На **существующей** — строку `DATABASE_URL` не удаляйте, см.
   «Пароль базы на старой установке»):
   ```bash
   cp .env.example .env
   sed -i "s/^VTX_SECRET_KEY=.*/VTX_SECRET_KEY=$(openssl rand -hex 32)/" .env
   sed -i "s/^POSTGRES_PASSWORD=.*/POSTGRES_PASSWORD=$(openssl rand -hex 16)/" .env
   ```
   По умолчанию порт приложения привязан к `127.0.0.1` (`APP_BIND`) — снаружи
   его не видно. Пока нет домена и HTTPS, для входа по IP откройте его:
   ```bash
   sed -i "s/^APP_BIND=.*/APP_BIND=0.0.0.0/" .env
   ```
   Когда поднят HTTPS через Caddy (см. «Домен и HTTPS»), верните `127.0.0.1`.
3. Запустите:
   ```bash
   docker compose up -d --build
   ```
4. Откройте порт в firewall / Security Group ВМ:
   ```bash
   sudo ufw allow 8000/tcp
   ```
5. Зайдите на `http://<IP-сервера>:8000`, зарегистрируйте админа.

Контейнер поднимается с `restart: unless-stopped` — сам стартует после перезагрузки
сервера. Состояние лежит в ДВУХ местах, и бэкапить нужно оба:
- **база Postgres** (том `pgdata`) — аккаунты, сессии, задачи, настройки, токены,
  ключи, карточки встреч:
  `docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql`
  (пользователь и база берутся из окружения самого контейнера);
- **папка `./data`** на хосте — файлы: загрузки, результаты, записи.

> Для публичного домена дальше нужен HTTPS-прокси — см. «Домен и HTTPS».

## Аккаунты и вход

- Весь сайт закрыт логином. **Первый зарегистрированный аккаунт = основатель
  сервера** (только ему доступны серверные операции: установки, серверный HF-токен).
- Модель — **команды**: регистрация без кода создаёт СВОЁ пустое рабочее
  пространство (вы — его админ); регистрация с **кодом приглашения** админа
  (виден у него в «Профиле», меняется раз в сутки) подключает к его команде —
  общие настройки, токены и ключи.
- ⚠ **Регистрация всегда открыта**: любой, кто знает адрес, может создать себе
  отдельную команду (чужих данных он не увидит). Если это неприемлемо — закройте
  доступ на уровне прокси/VPN; переключателя «запретить новые команды» в
  приложении пока нет.
- Пароли хранятся как PBKDF2-хеши; токены Weeek/облаков — зашифрованы **отдельным
  ключом под каждый логин** (выводится из `VTX_SECRET_KEY`). Один пользователь не
  видит данные и секреты другого.
- Подробнее и тест-кейсы — [docs/БЕЗОПАСНОСТЬ.md](docs/БЕЗОПАСНОСТЬ.md).

> **Важно:** задайте свой `VTX_SECRET_KEY` до первого сохранения токенов и держите
> его вне git. Если он пустой — ключ генерируется в `data/secret.key`.

## Протокол встречи (LLM)

Распознавание работает без ключей; для **протокола** нужен движок. На сервер Ollama
**не ставится** — её нужно **подключить снаружи** (или использовать облако по ключу).

**A. Ollama — бесплатно, локально, но ВНЕШНЯЯ (у Ollama нет API-ключа):**
Поставьте её на этой же машине (на хосте, вне Docker) или на отдельном сервере:
```bash
curl -fsSL https://ollama.com/install.sh | sh
OLLAMA_HOST=0.0.0.0 ollama serve        # чтобы принимала подключения из контейнера
ollama pull qwen2.5:7b                   # модель для протокола (~4.7 ГБ)
```
Затем в `.env` приложения укажите её адрес:
```
OLLAMA_URL=http://host.docker.internal:11434   # Ollama на ЭТОЙ машине (хост)
# OLLAMA_URL=http://192.168.1.50:11434          # Ollama на другом сервере
```
и `docker compose up -d`. (По умолчанию `OLLAMA_URL` уже указывает на хост — если
Ollama там, можно ничего не менять.)

**B. Облако по ключу:** впишите в `.env` `GROQ_API_KEY` (бесплатный тариф),
`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `GIGACHAT_AUTH_KEY`, `YANDEX_API_KEY`+
`YANDEX_FOLDER_ID` — и `docker compose up -d`. В интерфейсе у каждого провайдера
можно выбрать **тариф/мощность модели**.

### Серии встреч, контекст и задачи в Weeek (09.2026)

- **Карточка серии** («Контекст для ИИ» → «Повторяющиеся встречи»): для
  повторяющейся встречи Weeek задаются проект, участники и роли, цели, термины,
  тип протокола и приоритет («только запись» отключает протокол). Карточка и
  итоги прошлой встречи серии читаются моделью ПЕРЕД расшифровкой. Черновики
  карточек — `docs/series-seed.json`, импорт — `scripts/import_series_context.py`.
- **Порядок протокола** — для руководителя: кратко → решения → задачи (со
  сроком) → мелкие → сделано → выводы и открытые вопросы → темы → мысли.
- **Задачи → в Weeek**: на странице протокола таблица черновиков с исполнителем
  из воркспейса, сроком и основанием-цитатой; «Создать в Weeek (N)». Настройки —
  на странице Weeek (проект/доска/колонка, авторежим выключен по умолчанию).
  Перед первым использованием проверьте одну задачу в тестовом проекте.
- **Текст с экрана**: ключи и пароли маскируются до отправки в модель.

Подробности и бэклог — `docs/РЕВЬЮ-2026-09-01.md`.

## Бот-рекордер Телемоста

Включён при `VTX_RECORDER_ENABLED=1` (по умолчанию). При старте `docker/run.sh` поднимает:
- **Xvfb** — виртуальный экран `:99` (`VTX_SCREEN_RES`), Chromium открывается на весь экран;
- **PulseAudio** + **null-sink `meet0…meetN`** (по одному на слот записи) как
  устройство вывода браузера — ffmpeg пишет его монитор `meet0.monitor`.
  Создаётся при старте, настраивать ничего не нужно.

Бот заходит **с выключенными микрофоном и камерой** и ничего не транслирует.
Настройки (токен Weeek, облако, режим входа, какие встречи писать) — на странице
**`/automation`**; проверка — кнопки «Тест записи» и «Проверить звук».

Чтобы гонять **без бота** (только распознавание/протокол) — `VTX_RECORDER_ENABLED=0`.

| Переменная | По умолч. | Назначение |
|---|---|---|
| `APP_PORT` | 8000 | внешний порт |

| `VTX_CPU_THREADS` | 4 | число потоков CPU |

| `VTX_RECORDER_ENABLED` | 1 | бот-рекордер (Xvfb+Pulse); 0 = только распознавание |
| `VTX_SCREEN_RES` | 1920x1080x24 | размер виртуального экрана бота |
| `VTX_PULSE_MONITOR` | meet.monitor | PulseAudio-источник звука встречи |
| `VTX_SECRET_KEY` | — | **ключ шифрования секретов** (задайте свой на сервере!) |
| `VTX_HTTPS` | 0 | `1` = cookie с флагом Secure (за HTTPS-прокси) |
| `VTX_SESSION_TTL_HOURS` | 168 | срок жизни сессии |
| `VTX_EMBED_PROVIDER` | — | эмбеддинги памяти встреч: `yandex` / `gemini` / `ollama`; пусто = поиск по встречам только полнотекстом (нужен образ базы `pgvector/pgvector:pg16`, уже в compose) |
| `VTX_EMBED_MODEL`, `VTX_EMBED_DIM` | по провайдеру | модель и размерность вектора; менять после первого включения — только с пересчётом (`scripts/embed_backfill.py`) |
| `VTX_VERIFY_WINDOWS` | 0 | `1` = проверка цитат по окнам вокруг якорей пунктов, а не по всей расшифровке в каждом батче |

## Обновление и обслуживание

**На боевом сервере обновляйтесь скриптом** — он не убьёт идущую работу:

```bash
bash scripts/update.sh
```

Скрипт сначала спрашивает у сервиса, занят ли он записью или распознаванием, и
только потом собирает. Пересборка вслепую посреди часовой встречи означает
потерянную запись и час работы процессора впустую. Обойти проверку — `--force`.

Скрипт останавливается и ничего не собирает, если:
- в рабочей копии есть незакоммиченные правки отслеживаемых файлов — откатите
  (`git checkout -- <файл>`), отложите (`git stash`) или соберите с ними:
  `bash scripts/update.sh --allow-dirty`;
- база не ответила на вопрос о занятости (контейнер `db` лежит, `psql` с
  ошибкой) — это не «0 задач»; если база лежит и обновление должно её поднять —
  `--force`;
- скачанные изменения не применяются (ветка разошлась с сервером);
- `docker compose config` не проходит или адрес базы у `app` не сходится с
  сервисом `db` (`scripts/check_compose_config.py`);
- **с новыми настройками приложение не войдёт в базу** — скрипт пробует войти
  из работающего контейнера `app` до сборки (см. ниже про пароль).

Если репозиторий недоступен (сеть), собирается текущий код — правки `.env`
всё равно применятся. Базу скрипт поднимает раньше приложения: том, созданный
образом `postgres:16-alpine`, на `pgvector/pgvector:pg16` (glibc) требует
перестройки текстовых индексов — скрипт делает `REINDEX DATABASE` сам, один
раз (порядок сортировки строк у musl и glibc разный).

### Пароль базы на старой установке

Postgres берёт `POSTGRES_PASSWORD` **только при создании тома** `pgdata`; потом
это просто строка в `.env`, и её смена пароль роли в базе не меняет. Установки,
поднятые до 30.10.2026, создавали том с паролем `voise`, и приложение входит в
базу лишь благодаря строке в `.env`:

```
DATABASE_URL=postgresql://voise:voise@db:5432/voise
```

**Не удаляйте её**, пока пароль роли не сменён — иначе приложение после
перезапуска не войдёт в базу (`update.sh` это поймает и не перезапустит, но
ручной `docker compose up -d` — нет). Смена, когда ничего не идёт:

```bash
# 0. Бэкап базы и .env
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-$(date +%F).sql
cp .env .env.bak-$(date +%F)
# 1. В .env — свой POSTGRES_PASSWORD (не voise). Строку DATABASE_URL пока НЕ трогаем.
# 2. Пароль роли := POSTGRES_PASSWORD из .env. Пароль идёт по конвейеру,
#    в командной строке и истории его нет:
docker compose config --format json \
  | python3 scripts/check_compose_config.py --alter-role-sql \
  | docker compose exec -T db sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
# 3. Сразу же убрать строку и перезапустить приложение (между шагами 2 и 3
#    новые подключения старого контейнера не проходят — делайте подряд):
sed -i '/^DATABASE_URL=/d' .env
docker compose up -d app
# 4. Проверка: строгая сверка конфига и живой вход
docker compose config --format json | python3 scripts/check_compose_config.py --fresh
docker compose logs --tail 30 app
```

Откат, если после шага 3 приложение не входит: `cp .env.bak-<дата> .env`, затем
`echo "ALTER ROLE voise WITH PASSWORD 'voise';" | docker compose exec -T db sh -c 'psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB"'`
и `docker compose up -d app`.

Пароль может содержать любые символы: compose передаёт его приложению
отдельно (`PGPASSWORD`), а не внутри адреса. Только во внешнем `DATABASE_URL`
символы `@ # / ? %` нужно экранировать (`%40 %23 %2F %3F %25`).

Вручную (когда точно ничего не идёт):

```bash
git pull                      # забрать изменения
docker compose up -d --build  # пересобрать и перезапустить
```
⚠️ Первое обновление после смены образа базы на `pgvector/pgvector:pg16` —
только скриптом: вручную `REINDEX` не делается (см. выше).
- Логи: `docker compose logs -f app` (уровень — `VTX_LOG_LEVEL`)
- Бэкап: `pg_dump` базы (том `pgdata`) **и** папка `./data` — см. «Раскатка на сервере».
- Модель на лету: `VTX_MODEL=medium docker compose up -d` (первый запрос докачает её).

## Домен и HTTPS

Сертификат выпускает и продлевает **Caddy** — certbot и cron не нужны.

**Сначала, до запуска:**
1. **A-запись** домена → IP сервера. Проверить: `dig +short ваш-домен`.
2. **Порты 80 и 443** открыты в firewall (`ufw allow 80,443/tcp`) **и в группе
   безопасности ВМ**. Порт 80 обязателен: по нему Let's Encrypt проверяет домен.

**Затем — одной командой:**
```bash
sed -i 's/^DOMAIN=.*/DOMAIN=ваш-домен.ru/; s/^ACME_EMAIL=.*/ACME_EMAIL=вы@почта.ru/; s/^COMPOSE_PROFILES=.*/COMPOSE_PROFILES=https/; s/^VTX_HTTPS=.*/VTX_HTTPS=1/; s/^VTX_TRUST_PROXY=.*/VTX_TRUST_PROXY=1/' .env && docker compose up -d
```

Через полминуты сайт откроется по `https://ваш-домен.ru` с валидным
сертификатом. Прогресс выпуска виден в `docker compose logs -f caddy`.

Что делают переменные:
- `DOMAIN`, `ACME_EMAIL` — домен и почта для уведомлений Let's Encrypt;
- `COMPOSE_PROFILES=https` — включает сервис `caddy` при обычном
  `docker compose up -d` (иначе каждый раз нужно дописывать `--profile https`);
- `VTX_HTTPS=1` — куки сессии получают флаг `Secure`;
- `VTX_TRUST_PROXY=1` — приложение читает реальный IP из `X-Forwarded-For`.
  **Без прокси эту переменную ставить нельзя** — IP можно будет подделать.

Сертификаты лежат в томе `caddy_data` и переживают пересоздание контейнеров:
иначе при каждом перезапуске выпускался бы новый и упёрлись бы в лимит
Let's Encrypt (5 штук в неделю на домен).

После перехода на домен порт 8000 наружу не нужен — закройте его в группе
безопасности, оставив 80 и 443. Внутри compose приложение остаётся доступным
Caddy по внутренней сети.

## Решение проблем

- **`docker compose` не найден** — нужен Compose v2 (плагин); на старых системах
  команда `docker-compose` (с дефисом).
- **Долго «Загрузка модели…»** на первом запросе — модель Whisper качается один раз,
  потом кэшируется в `./data`.
- **Протокол не собирается** — не выбран движок: поднимите Ollama отдельной службой (`OLLAMA_URL`)
  + `scripts/setup-ollama.sh`) или задайте облачный ключ.
- **Нет доступа снаружи** — проверьте `APP_BIND=0.0.0.0` в `.env` (по умолчанию
  `127.0.0.1`, порт виден только с самого сервера) и откройте порт:
  `sudo ufw allow 8000/tcp`.
- **OOM / мало памяти** — `VTX_MODEL=small`, без диаризации, без Ollama на маленькой ВМ.
- **Бот не заходит / запись пустая** — проверьте `/automation` → «Тест записи» и
  «Проверить звук»; вёрстка Телемоста иногда меняется (селекторы в
  `app/automation/recorder/browser.py`).

## Без Docker (запасной путь)

В репозитории есть `deploy.sh` (venv + ffmpeg) и `voicetx.service` (systemd) — для
запуска ядра без контейнеров. Docker — рекомендуемый путь; бот-рекордеру при этом
всё равно нужны Xvfb + PulseAudio на хосте.
